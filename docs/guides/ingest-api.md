# 收单 API 合约

供个人快捷指令、通知转发及其他自己控制的调用方使用。数据库操作由服务器完成；手机不需要数据库账号。与普通登录 JWT 分开，使用 `.env` 中的 `INGEST_TOKEN`。

## 鉴权与账户

- 请求头：`x-ingest-token: 自己的配置值`，或 `Authorization: Bearer 自己的配置值`。不要放在 URL 参数中。
- 未配置令牌时返回 `503`，错误或缺失令牌返回 `401`。
- `INGEST_USER` 可指定写入用户 ID；未指定时使用数据库中第一个用户，适合当前固定单用户形态。用户不可用时返回 `503`。
- 接口只确认请求已写入服务器，不会替微信、支付宝或银行发起付款/退款。

## 文本识别：POST /api/ingest/ocr

支持 JSON、`application/x-www-form-urlencoded`、`text/plain`。为兼容现有快捷指令，也保留 POST 查询参数方式；交易原文可能进入 URL 日志，推荐使用请求体。

| 字段 | 必填 | 格式与含义 |
|---|---|---|
| `text` | 是 | 1–5000 字的原文；也接受通知对象的 `title`/`subtitle`/`body`/`message`/`信息` 等文本字段，合并后仍限 5000 字 |
| `date` | 否 | 有效本地日期 `YYYY-MM-DD`，显式覆盖文本日期 |
| `time` | 否 | 24 小时 `HH:mm:ss`，也接受 `HH:mm` 并补 `:00`，显式覆盖文本时间 |
| `eventId` | 否 | 1–128 字；来源交易号或同一事件重试保持不变的标识 |

```json
{
  "text": "支付成功\n实付金额：¥35.50\n商户：便利店\n支付时间：2026-10-04 12:34:56",
  "eventId": "wechat-order-20261004-001"
}
```

解析顺序先核对最终支付/退款状态，再选择本次交易金额。未完成、失败、只有符号或金额而没有可信交易状态的内容不自动入账；收款、转入、入账、进账、存入、汇入、工资、奖金、利息、报销等“钱进来”的通知按退款入账（工资、利息等纯收入也会记为退款），条件与营销文案（「最高返还」「支付成功后可返还」）不算退款。退款页同时出现原订单金额时，应选择明确关联本次已完成退款的金额。多笔详情混在同一文本或金额冲突时，先拆成单笔或手工核对。

「退款金额／本次退款／实退金额」用于选择金额，单独出现不代表已到账；申请页、需确认及「可原路返回」等政策文案不算完成退款。退款详情应包含「退款成功／到账／已全额退款／已返还」等完成证据。银行账户通知中的快捷支付退款可按通知上下文与紧邻退款金额识别，不能仅凭出现「支付退款」几个字记账。

省略完成状态的银行快捷退款模板仅支持个人账户末四位、可选日期时间、紧邻金额，以及结束、明确余额或查看详情提示。金额后有待确认、审核或陌生说明时保守拒绝；请使用已完成的详情页或人工核对后调用结构化接口。

日期：显式 `date` → 文本交易日期 → 接收日期。OCR/通知时间：显式 `time` → 可识别的消息交易时间 → 本次请求接收时刻（精确到秒），这是用户指定的实时通知规则。手机状态栏时间不作为消息交易时间。消息提供分钟时补 `:00`；这不是从原文获得的真实秒数。没有年份的银行月日通知按显式 `date` 或接收日期选择最近唯一合法年份；历史截图年份无法确定时请传 `date`。

商家只取明确的商户名称/收款对象字段；摘要、银行名、财付通等支付通道不推断为商家。未知保存 `null`，界面显示「商家未记录」。支出近义词覆盖支付/付款/付费/消费/扣款/扣费/花费/支取/取现/转出/缴费/还款与「发生一笔…的消费」句式；退款近义词覆盖退款/退回/退还/退货/退单/退费/冲正/返款/返还/撤销/原路退回。福建农信已出账支出、招行发生快捷支付扣款模板已用匿名样本覆盖；收款/入账通知（如「您账户1234于10月05日01:17收款人民币0.01」「您尾号1234的账户网联 入账收入0.02元」）按退款入账。银行邮件通道（IMAP）仍把收入/转入类邮件记为不记账，二者互不影响。

通知对象示例（标题可省略）：

```json
{
  "text": {
    "title": "银行动账通知",
    "body": "您尾号1234的账户出账 网联支出1.23元，点此查看详情"
  }
}
```

也接受顶层 `notification` 包装及单元素数组；多条通知数组、同一正文槽的不同内容、外层与包装层内容冲突均拒绝。未知对象不会自动 `stringify`。提取失败的 `400` 返回 `invalidFields` 和 `inputShape`（字段名、类型、长度）。服务端结构日志用于诊断快捷指令实际输入，不记录请求头令牌或完整通知原文。

## 结构化入账：POST /api/ingest/transaction

支持 JSON 与 `application/x-www-form-urlencoded`，由调用方先确认交易成功和准确金额。

| 字段 | 必填 | 格式与含义 |
|---|---|---|
| `type` | 是 | `expense` 支出，`refund` 退款 |
| `amount` | 是 | 正数元，最多两位小数；数字或数字字符串，不能传负数、货币符号或千分位分隔符 |
| `date` | 否 | 有效日期 `YYYY-MM-DD`；缺省今天 |
| `time` | 否 | `HH:mm:ss` 或 `HH:mm`；缺省请求接收时刻 |
| `merchant` | 否 | 商户文字，最长 128 字 |
| `note` | 否 | 备注，最长 256 字 |
| `eventId` | 否 | 1–128 字，建议传稳定来源交易号 |

```json
{
  "type": "refund",
  "amount": "20.00",
  "date": "2026-10-04",
  "time": "18:02:09",
  "merchant": "便利店",
  "note": "通知确认退款到账",
  "eventId": "wechat-refund-20261004-001"
}
```

## 响应、时间与重试

| HTTP 状态 | 含义 |
|---|---|
| `201` | 新建，`duplicate: false` |
| `200` | 重复事件，`duplicate: true`，返回已有交易 |
| `400` | 参数格式错误，未入账 |
| `401` | 令牌错误，未入账 |
| `409` | 同一 `eventId` 对应不同交易内容，需要核对 |
| `422` | 文本未匹配明确支付/退款交易，未入账 |
| `503` | 未配置收单或没有可用账户，未入账 |

成功响应包含 `message` 与 `transaction`。交易日期字段为 `occurredAt`（`YYYY-MM-DD`），时间字段为 `occurredTime`（`HH:mm:ss` 或 `null`）。数据采用本地业务日期/时间，不接收 UTC 偏移；当前部署按 Asia/Shanghai 使用，异地来源应在调用前转换到自己的业务时区。

- `eventId` 是同一来源事件的稳定标识；不要重试时重新生成。付款与退款应使用不同事件 ID。
- 无事件 ID 时用类型、日期、来源时间、金额与商户生成内容键；来源没有时间时再包含 NFKC 规范化并合并空白后的完整文本（结构化请求没有文本，使用空串）。OCR 的接收时刻只用于展示，不参与该指纹；重复发送仍返回第一次记录的时间。同日同金额的退款与支出不互相吞掉，有不同来源秒级时间的付款分别保留。
- 缺少时间、交易号和商户等区分信息时，实际多笔交易可能无法区分。没有来源日期时无 ID 指纹按接收日期分组；跨午夜重试可能被当成次日新交易，不能与次日真实同文等额交易可靠区分。提供稳定 `eventId` 可跨午夜保留首次日期时间；不要靠添加任意当前时间规避去重。
- 文本与结构化收单共享该幂等机制，保存来源均为 `ocr`；同一 `eventId` 改变类型、金额、明确提供的来源日期/时间或商户会返回 409。未知来源日期/时间的接收日期/秒变化不视作冲突。备注不作为不同交易的判定字段。
- 唯一键保护收单并发重试。旧记录没有收单键，不参与新键的强幂等；邮件、CSV、手工记账等来源并非自动共享同一银行交易号。
- 网络超时不一定代表未写入。用原 `eventId` 重试并查看响应，或先查账本。当前没有离线队列，网络恢复后需由调用方重试。

历史记录原本没有时间，迁移后仍为 `null`。`HH:mm` 补成 `HH:mm:00` 是兼容输入格式，来源实际精度仍只有分钟。

普通 JWT 交易接口 `POST /api/transactions` 也支持可选 `requestId`（1–128 字）：用于手工保存与 CSV 导入的网络重试，同一次写入保持相同 ID。新建返回 `201`，相同参数重试返回 `200` 与原交易，内容冲突返回 `409`。该 ID 不在响应中公开，不能通过交易编辑改写。`eventId` 与 `requestId` 使用不同命名空间。

收单保持原始流水，无法从银行摘要确认房租等用途时不猜。入账后在账本点开交易「分摊到固定支出」，可按金额关联多项；登录接口 `PUT /api/transactions/:id/fixed-allocations` 原子替换，空数组撤销。快捷指令请求不需要改动，也不能用收单令牌编辑分摊。完整金额、退款与跨期规则见 [固定支出指南](fixed-expenses.md)。旧 `POST /api/bills/:id/pay` 在同一事务创建交易、支付标记和分摊；删除付款也清除关联，但不能让已有固定退款失去付款覆盖。普通退款流水保留，原交易删除后解除其 `refundOfId`。

## 调试约定

服务端日志记录收单结果和诊断信息，不输出完整 OCR/通知原文及令牌。修改解析规则时先在 `server/src/ingest/payment.test.ts` 添加匿名样本失败测试，路由规则在 `server/src/routes/ingest.test.ts` 做隔离数据库测试；真实样本应先遮盖卡号、姓名、交易号和隐私备注。
