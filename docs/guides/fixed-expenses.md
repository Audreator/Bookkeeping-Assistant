# 指南：把真实付款分摊到固定支出

银行卡通知通常只有金额，无法确认是房租、水费还是普通消费。收单继续保留通知中的原金额、商家和交易时间；由自己在账本明确指定固定用途，不根据商家或分类猜测。

## 手机上怎么操作

1. 进入「设置 → 固定支出」，建立房租、水费等账单，填写计划金额和每月到期日。账单是预算计划，添加账单不会生成一笔假付款。
2. 快捷指令通知、截图 OCR、CSV 导入或手工记账完成后，在「今天」或「账本」点开那笔真实交易。
3. 点击「分摊到固定支出」。选择账单，填写属于它的金额及具体到期日；一笔付款可以添加多项，也可以分摊到同一账单的不同月份。
4. 检查原流水金额、固定分摊合计和剩余日常金额，点右上角蓝色「✓」或底部「保存分摊」。两者保存同一组分摊；左上角「×」关闭，不保存本次修改。分摊保存与交易编辑各有自己的保存入口；修改交易内容时先保存，再分摊。
5. 账本仍显示原始付款的完整金额，并显示固定分摊标记；设置页显示本月到期账单的实际已付净额和剩余金额。未付足显示部分支付，不会因为关联了一笔就算全部付清。

例如银行卡扣了 900 元，实际是房租 800、水费 50、另外日常购买 50。添加两项：房租 800、水费 50；保留 50 为日常。无需把原流水拆成三笔，也无需再新增一笔房租。这样统计仍是实际支出 900，日常预算只扣 50。

撤销全部关联时，先点「取消全部分摊」，再点「✓」或「保存分摊」才会提交。只清空后关闭弹窗，原有分摊仍保留。灰色确认按钮表示正在加载、保存或交易尚未确认，请等待或先确认交易。

| 实际情况 | 分摊方式 |
|---|---|
| 一笔 800 元全是房租 | 房租 800，剩余日常 0 |
| 一笔同时交房租、水费 | 每项各填实际金额，分摊合计不超过付款 |
| 房租分两次各交 400 | 在两笔流水分别关联相同的房租到期日，各填 400 |
| 一次提前交数月房租 | 同一房租按不同到期日分别添加，填写对应金额 |
| 计划 800，实际房租 850 | 可分摊 850，实际超出计划的 50 也占用固定预算 |
| 关联错了 | 打开分摊，调整或撤销；原流水保留 |

已有快捷指令的 JSON、请求头和收单地址无需改动。固定分摊使用登录后的业务接口，不向通知快捷指令暴露登录 JWT，也不把 `x-ingest-token` 当成编辑权限。

## 预算怎么计算

开启「固定支出预留」时：

- 本期日常净支出 = 本期实际净流水 − 本期固定净付款。
- 本期固定预算 = 本期固定净付款 + 本期到期账单尚未覆盖的计划余额。
- 本期可花预算 = 原设置预算 − 本期固定预算。

房租计划 800，在本期付了 600 后，固定预算仍为 800（实际付款 600 + 尚付余额 200）。整笔付清后仍为 800，日常不会再次扣 800。实际付超计划时按实际金额占预算，金额不会凭空消失。

日常净额可以因退款／收入多于支出而为负；首页把它解释为正数「净入账」并显示 0% 使用比例，不把负净额当作负消费。例如付款 900 中固定 850、日常 50，再日常消费 17.23，收到未指定固定用途的退款 150，则日常净入账为 82.77，完整补回日常余额。若这笔退款其实退的是房租，应按下面规则明确分摊，避免误把固定退款当作日常回款。

跨期按实际付款日占用现金预算：上月提前付本月房租，本月已覆盖的计划不再次预留；本月补付上月房租，本月实际付款会占本月固定预算。历史期间保持原始现金流水计算结转，仅当前期间使用分摊抵扣日常，避免跨月或月/周切换后产生免费结余。

当前期内已确认且截至今天的付款/退款才参与覆盖；未来日期不会提前释放预留。关闭预留时所有真实流水全额按普通日常支出/退款计算，分摊记录仍保留。首页日常预算与「统计」的实际支出因此可能不同，统计始终保留完整原流水。

## 退款、修改和删除

固定退款必须明确指定其退回的账单和原所属到期日。混合退款中只有指定的固定部分恢复固定账单的未付余额，剩余部分正常补回日常预算；普通收入不会自动推断为房租退款。

例如原 900 元付款有房租 800 + 日常 100，本次退 150，其中退租 100 + 日常退 50：在退款分摊里指定房租 100。固定已付净额变成 700、尚付余额 100；日常退款为 50。退款分摊不能超过该账单该期已有未退的固定付款。退款发生在后续期间时，按本次退款日归还现金预算，可能使本期固定预算为负，这是历史固定款退回的正常结果。

每项金额必须为正数且最多两位小数，合计不得超过原交易。只允许已确认交易分摊；交易金额不能下调到小于已分摊合计。已有分摊时若需改交易类型或状态，先撤销分摊再改。需要删除/撤销付款、且会使已有固定退款失去付款覆盖时，先撤销或调整那笔退款的分摊，再处理原付款。

有真实分摊的账单保留历史关联，不能直接删除；不再需要时选择停用。停用停止产生未付计划预留，已发生固定付款仍计入实际现金预算。修改名称、金额、每月到期日会更新当前计划，已经保存的实际分摊金额和所属到期日保持原样。

旧的「已付」标记没有准确分摊金额时，仅作为历史标记展示，不凭空增加可花预算。数据库迁移只为可以核对原支出金额的旧关联回填分摊，歧义关联需要自己检查。

## 备份与业务接口

普通和加密备份都包含 `data.allocations`。恢复时先创建账单和交易，再映射新 ID 恢复分摊，付款分摊先于退款分摊恢复。所有旧支付标记只恢复历史标记，不推断分摊金额；旧备份没有该字段时仍可导入，需要自己指定用途后才抵扣日常。恢复是追加式，重复导入会增加数据，请先核对目标账本。

登录 JWT 接口：

```http
PUT /api/transactions/123/fixed-allocations
Authorization: Bearer <自己的登录JWT>
Content-Type: application/json
```

```json
{
  "allocations": [
    { "billId": 1, "periodKey": "2026-10-05", "amount": 800 },
    { "billId": 2, "periodKey": "2026-10-05", "amount": 50 }
  ]
}
```

上述 ID、金额和日期是合成示例。一次请求原子替换这笔交易的全部分摊；传 `{"allocations":[]}` 撤销全部。同一交易、账单和到期日不能重复，最多 48 项。`periodKey` 是具体的 `YYYY-MM-DD` 到期日，支持提前付或补付，不能只写月份。`GET /api/bills` 返回账单、历史支付标记和全量 `allocations`；`GET /api/transactions` 的 `fixedAllocations` 供列表显示。

参数格式或分摊合计超出交易金额返回 400；越权或不存在返回 404；退款覆盖不足、受关联保护的修改删除返回 409。退款日期不能早于覆盖它的实际付款日期，移动日期时也会重校验。单次分摊请求失败后原流水与原分摊保持不变，不会只写入一半；备份恢复为多次追加请求，中断后先核对已恢复数据再继续。
